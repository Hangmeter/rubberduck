Регламент разработки проекта RubberDuck
Настоящий документ определяет жесткие требования к архитектуре, технологическому стеку и правилам написания кода для ИИ-агента Codex Web. Любые Pull Request'ы, нарушающие эти правила или содержащие неутвержденные сторонние библиотеки, будут автоматически отклонены.
1. Разрешенный технологический стек и окружение
- Язык разработки: Чистый JavaScript (Node.js) — ESM или CommonJS (строго без TypeScript).
- Базовая ОС сервера: Alpine Linux внутри контейнеров (Docker Compose v2).
- Среда бэкенда: Node.js (LTS 18+ / 20+).
- База данных: PostgreSQL 15 (Alpine).
2. Белый список разрешенных библиотек и фреймворков
ИИ-агенту разрешено использовать только следующие зависимости:
- fastify (версии ^5.0.0) — основной веб-фреймворк для REST API и маршрутизации.
- @fastify/static (версии ^8.0.0) — строго для раздачи статических файлов фронтенда.
- pg (официальный драйвер PostgreSQL) — для создания пула соединений и выполнения сырых запросов.
КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО: Использовать любые ORM (Prisma, Sequelize, TypeORM), query-билдеры (Knex) или сторонние валидаторы (Zod, Joi), если они явно не запрошены в тексте Issue. Валидация должна выполняться стандартными средствами Fastify (JSON Schema) или нативной проверкой типов в JS/PostgreSQL.
3. Требования к фронтенду (Клиентская часть)
Фронтенд стягивается как статика с бэкенда. Он должен оставаться ультралегким:
- Интерфейс: Чистый HTML5, ванильный CSS3 (без Tailwind, Bootstrap и т.д.), чистый JavaScript (Vanity JS).
- Общение с бэкендом: Строго через асинхронные запросы fetch() к REST API бэкенда.
- Без сборщиков (без Webpack, Vite) и без фронтенд-фреймворков (React, Vue, Angular).
4. Правила работы с базой данных PostgreSQL
- Никакой генерации схем на лету: Текущая схема данных фиксирована в файле init.sql и задокументирована. Все таблицы, связи, индексы и перечисления (ENUM) создаются строго на уровне СУБД.
- Сырой SQL: В коде бэкенда запросы пишутся в виде явных SQL-строк (например, client.query('SELECT ...')).
- Безопасность: Использовать исключительно параметризованные SQL-запросы (например, VALUES ($1, $2)) для полной защиты от SQL-инъекций.
5. Стиль кода и ограничения для Codex
- Код должен быть максимально лаконичным, плоским и читаемым для человека (без избыточных абстракций, фабрик фабрик и лишних слоев).
- При изменении кода всегда сохранять существующую логику пула соединений (pg.Pool).
- Все новые эндпоинты должны логически расширять единый файл server.js (или структуру, утвержденную в рамках конкретной задачи) без раздувания кодовой базы.
6. Автоматическое ведение документации (Обязательно)
При изменении существующего кода, добавлении эндпоинтов или изменении БД, ИИ-агент ОБЯЗАН в рамках того же Pull Request атомарно обновить следующие файлы:
- **REST API**: Любые изменения путей, параметров или ответов бэкенда должны быть синхронно отражены в файле `doc/api/openapi.yaml` строго в формате OpenAPI 3.0.
- **Структура БД**: Если меняется файл `init.sql` (добавляются таблицы, поля или индексы), агент обязан обновить структуру и текстовое описание таблиц в файле `doc/db_schema.md`.
- **Комментарии в коде**: Новый функционал бэкенда должен быть снабжен лаконичными комментариями на русском языке (почему и как это работает), без избыточного комментирования очевидных строк.
